# Vue ESLint Parser Compatible Parser Spec

This spec defines the target architecture and implementation rules for producing a `vue-eslint-parser` compatible AST.

This spec only covers the parser/toolkit work needed to produce a `vue-eslint-parser` compatible AST. JSX transform behavior is intentionally out of scope here.

## Goals

- Produce a `vue-eslint-parser` compatible AST without calling `vue-eslint-parser` in production code.
- Keep parser and toolkit responsibilities separate.
- Keep source locations compatible with ESLint consumers: JavaScript-facing offsets must be UTF-16 offsets.
- Keep parsing and diagnostic ownership in Rust / Oxc, not in toolkit JavaScript.

## Non-Goals

- Toolkit JavaScript should not become a second parser.
- Toolkit JavaScript should not infer template or script AST structure from source text.
- Toolkit JavaScript should not call `@typescript-eslint/parser`, `vue-eslint-parser`, or another parser outside tests.
- Toolkit JavaScript should not patch generated inner AST nodes by node type, except explicitly allowed metadata injection and transport normalization.

## Architecture Boundary

### Parser Crate

The parser crate owns Vue SFC parsing and `vue-eslint-parser` compatible V\* node serialization.

It should handle:

- SFC block parsing.
- Template lexer and parser behavior.
- V\* node structure.
- Template tokens and comments.
- Script tokens and comments collected through Oxc.
- Template expression parsing through Oxc.
- `VElement`, `VStartTag`, `VEndTag`, `VText`, `VExpressionContainer`, `VAttribute`, `VDirective`, and related V\* node fields, excluding template scope metadata.
- Node-level compatibility details such as text node segmentation, element namespace, style element metadata, directive expression shapes, and script body node serialization.
- Oxc diagnostics and raw parser errors.

The parser crate should not generate the final templateBody or serialize `references` or `variables` compatibility data. Template scope compatibility is a JavaScript compatibility concern and should be generated by toolkit using the same conceptual flow as `vue-eslint-parser`.

The parser crate should serialize a `VueSingleFileComponent`-like transport object, not a final `ESLintProgram`. The transport object may contain all inner compatible nodes and metadata needed by toolkit to build the root object.

### Toolkit Package

The toolkit package owns root-level rebuild and JavaScript-facing transport adaptation.

It may handle:

- Building the final root `Program`.
- Attaching `templateBody`.
- Attaching top-level `comments`, `tokens`, `range`, `loc`, and `sourceType`.
- Assigning `parent` links.
- Converting UTF-8 offsets from Rust into UTF-16 offsets for JavaScript / ESLint consumers.
- Parsing JSON or another transport format returned by native bindings.
- Normalizing transport-only ESTree differences explicitly allowed by this spec.
- Optional JS-only metadata injection explicitly defined by this spec.
- Generating template `references` and `variables` compatibility metadata.

It must not:

- Re-read source text to parse AST after receiving parser output.
- Reconstruct inner V\* node structure from source text.
- Define a separate parser error model independent of Oxc diagnostics and raw parser errors.
- Call `@typescript-eslint/parser` or `vue-eslint-parser` outside tests.
- Patch generated inner AST by `node.type`, except explicitly allowed transport normalization and metadata injection.

## Boundary Checks

Use these checks when reviewing parser/toolkit compatibility work:

1. If toolkit needs to read `source_text` after receiving parser AST for parsing use, the logic belongs in parser crate.
2. If toolkit defines or processes errors separately from Oxc diagnostics and raw errors, the logic belongs in parser crate or the diagnostic transport layer.
3. If `@typescript-eslint/parser` or `vue-eslint-parser` is called outside tests, the implementation is crossing the boundary.
4. If toolkit modifies generated AST by node type, the logic belongs in parser serialization or parser AST construction, except for top-level root rebuild, `parent` links, UTF-16 location conversion, explicitly allowed transport normalization, and explicitly allowed metadata injection such as template scope metadata.

## Source Text and Location Rules

Rust parser and Oxc should use UTF-8 byte offsets internally.

Toolkit should convert offsets to UTF-16 for JavaScript consumers. This conversion is allowed because it is transport adaptation, not parsing.

Toolkit may read source text for:

- UTF-8 to UTF-16 offset conversion.
- Line and column calculation.

Toolkit must not read source text to infer:

- Template AST structure.
- Script AST structure.
- Directive expression AST shape.
- Text node boundaries.
- Element namespace or tag semantics.

## Node Compatibility Rules

### Root Program

Toolkit should build the final root `Program` object from parser output.

The root `Program` should include:

- `type: "Program"`
- `body`
- `sourceType`
- `comments`
- `tokens`
- `range`
- `loc`
- `templateBody`

This is a top-level rebuild concern and belongs in toolkit.

### Template Body

Parser should produce compatible template V\* nodes.

Toolkit may select the top-level `<template>` VElement and attach it as `program.templateBody`.

Toolkit should not need to edit the inner template tree to make it compatible.

### Element Namespace

Parser should emit `namespace` on `VElement`.

Expected namespace behavior:

- Default namespace is HTML: `http://www.w3.org/1999/xhtml`.
- `<svg>` switches descendants to SVG: `http://www.w3.org/2000/svg`.
- `<math>` switches descendants to MathML: `http://www.w3.org/1998/Math/MathML`.

Example:

```vue
<template>
  <svg>
    <path />
  </svg>
</template>
```

Expected AST shape:

```text
VElement(template)
  namespace: HTML
  children:
    VElement(svg)
      namespace: SVG
      children:
        VElement(path)
          namespace: SVG
```

### Style Elements

Parser should emit `style: true` for style VElements when matching `vue-eslint-parser` behavior.

Example:

```vue
<style>
.button {
  color: red;
}
</style>
```

Expected AST shape:

```text
VElement(style)
  style: true
  children:
    VText(".button { color: red; }")
```

### Text Nodes

Parser should emit final compatible `VText` segmentation.

Adjacent text nodes should be merged when there is no semantic boundary that `vue-eslint-parser` preserves. Comments, interpolations, elements, and raw-text boundaries must follow `vue-eslint-parser` behavior.

Example:

```vue
<template>
  <div>hello {{ name }} world</div>
</template>
```

Expected AST shape:

```text
VElement(div)
  children:
    VText("hello ")
    VExpressionContainer(Identifier name)
    VText(" world")
```

### JavaScript Expressions

Parser should parse template expression regions as JavaScript fragments through Oxc.

Examples:

- `{{ x + y }}`
- `:foo="bar"`
- `v-if="ok"`
- `v-on:click="handleClick"`
- `v-for="item in items"`

The parser should preserve the source span of the Vue expression region while exposing the compatible expression node shape.

If Oxc emits AST nodes that differ from the `vue-eslint-parser` compatibility target, parser-side ESTree serialization may normalize them. Toolkit may also normalize explicitly allowed transport-only ESTree differences after JSON parsing.

### ESTree Transport Normalization

Toolkit may normalize `ParenthesizedExpression` by replacing it with its inner `expression`.

This exception exists because:

- Oxc may preserve parentheses as explicit `ParenthesizedExpression` nodes.
- `vue-eslint-parser` with `@typescript-eslint/parser` does not expose `ParenthesizedExpression` in the compatible AST shape.
- The normalization does not require reading source text or reparsing; it only rewrites an already parsed ESTree transport shape.

Example source:

```ts
const grouped = a + b + c
const object = { wrapped: foo }
```

Allowed toolkit normalization:

```text
ParenthesizedExpression(BinaryExpression(a + b)) -> BinaryExpression(a + b)
ParenthesizedExpression(Identifier(foo)) -> Identifier(foo)
```

No other Oxc ESTree node-type normalization is allowed by default. New cases must be added to this spec before implementation.

### BigInt

BigInt value conversion is allowed in toolkit because JSON cannot represent JavaScript `bigint`.

Parser may serialize enough metadata for toolkit to reconstruct `Literal.value` as `BigInt(...)` when required.

## Template Scope, Variables, and References

Template scope compatibility should follow the conceptual model used by `vue-eslint-parser`.

Rust parser should not output final `references` or `variables` fields. Toolkit should generate these fields after receiving the compatible template AST.

This is an explicit exception to the "toolkit must not modify generated AST by node type" rule. The exception is limited to template scope metadata:

- `VExpressionContainer.references`
- `VElement.variables`
- `Reference.variable`

Toolkit should still not use source text for parsing. It should use the expression AST already produced by the parser.

### Expression Parsing

Each Vue template expression should be treated as a local JavaScript fragment and parsed by the JS parser.

Examples:

```vue
<template>
  {{ x + y }}
  <div :foo="bar" />
  <div v-for="item in items" />
</template>
```

The expression parts are:

- `x + y`
- `bar`
- `item in items`

The parser should produce the expression AST for these regions. Toolkit should not call another parser for these expressions.

### Reference Collection

For each parsed JavaScript fragment, collect external references from the fragment's scope.

Example:

```vue
<template>
  {{ x + y }}
</template>
```

`x` and `y` are not declared inside this expression fragment, so they become `references`.

Conceptual metadata:

```text
VExpressionContainer
  expression: BinaryExpression(+)
    left: Identifier(x)
    right: Identifier(y)
  references:
    Reference(id -> Identifier(x))
    Reference(id -> Identifier(y))
```

Toolkit should follow the `vue-eslint-parser` model:

1. Treat the template expression as a local JavaScript fragment.
2. Run scope analysis over that fragment, equivalent to `eslint-scope`.
3. Collect references that are not declared inside the fragment.

The goal is equivalent behavior to `vue-eslint-parser` with `eslint-scope`: references are identifiers used by the expression that are not declared inside the expression fragment.

### Template Local Variables

Vue template local variables should be represented as `Variable` entries on the owning `VElement`.

Example:

```vue
<template>
  <div v-for="item in items">{{ item }}</div>
</template>
```

Expected conceptual shape:

```text
VElement(div)
  variables:
    Variable(id -> Identifier(item), kind: "v-for")
```

Other variable sources include slot scope variables and generic variables when matching `vue-eslint-parser` behavior.

Toolkit should create these variables from the parsed directive expression AST, not from source text. For example, `v-for="item in items"` already has a parsed left side and right side; `item` becomes a local variable for the owning element, while `items` remains a reference.

### Reference-to-Variable Resolution

After references and local variables are created, references should be resolved by walking from the current element to parent elements and matching variable names.

Conceptual algorithm:

```text
for each reference in current expression:
  element = nearest owning VElement
  while element exists:
    if element.variables contains variable with same name:
      reference.variable = variable
      break
    element = parent VElement
  if no variable is found:
    reference.variable = null
```

Example:

```vue
<template>
  <div v-for="item in items">
    <span>{{ item }}</span>
  </div>
</template>
```

Expected conceptual resolution:

```text
VElement(div)
  variables:
    Variable(item)
  children:
    VElement(span)
      children:
        VExpressionContainer({{ item }})
          references:
            Reference(item)
              variable -> Variable(item) from parent div
```

### Serialization Strategy

Rust-side parser should not serialize `references` or `variables` compatibility data.

Recommended approach:

- Parser emits compatible expression ASTs and directive expression structures.
- Toolkit walks the template AST after root rebuild.
- Toolkit runs scope analysis for each template expression using the already generated expression AST.
- Toolkit creates `VElement.variables` for Vue template local bindings such as `v-for` and slot scopes.
- Toolkit resolves references by walking from the current element to ancestor elements and matching variable names.
- Toolkit assigns `reference.variable` when a matching template variable is found.

This metadata injection should be isolated in one compatibility module so general AST rebuild code does not accumulate scattered type-specific patches.

The implementation should avoid serializing duplicated object graphs. References and variables should point to existing AST nodes in JavaScript memory.

If a future non-JSON transport can preserve object identity, the implementation may move this metadata construction earlier. Until then, toolkit is the correct place to build object links for `references` and `variables`.

### Scope Processing Flow

The intended flow mirrors `vue-eslint-parser`:

1. Parse each template expression as a JavaScript fragment.
2. Use scope analysis to find references inside the fragment.
3. Create Vue template variables from local binding positions such as `v-for` left-hand bindings.
4. Resolve each reference by walking from the current element to parent elements and matching variables manually.

## Diagnostics Rules

Parser should report diagnostics through Oxc diagnostics or raw parser errors.

Toolkit may convert diagnostic spans from UTF-8 to UTF-16 and map diagnostics into public transport shapes.

Toolkit should not:

- Invent separate parse error categories.
- Reinterpret parser diagnostics based on source text.
- Hide or rewrite Oxc diagnostics beyond transport formatting.

## External Parser Rules

`vue-eslint-parser` and `@typescript-eslint/parser` are allowed only in tests.

Allowed uses:

- Compatibility tests.
- Snapshot comparison.
- Fixture-based behavior investigation.

Disallowed uses:

- Runtime parsing.
- Toolkit fallback parsing.
- Parser crate behavior implementation.
- Production dependency on either parser.

## Implementation Checklist

Use this checklist before merging compatibility work:

- [ ] Parser emits compatible V\* node fields for all inner template nodes touched by the feature.
- [ ] Toolkit only performs root rebuild, parent links, location conversion, transport parsing, BigInt conversion, explicitly allowed transport normalization, and explicitly allowed template scope metadata generation.
- [ ] No production code calls `vue-eslint-parser`.
- [ ] No production code calls `@typescript-eslint/parser`.
- [ ] Toolkit does not inspect `source_text` to infer AST structure.
- [ ] Toolkit does not branch on inner node types to patch compatibility fields, except for explicitly allowed transport normalization and the isolated template scope metadata module.
- [ ] Diagnostics originate from Oxc diagnostics or raw parser errors.
- [ ] Tests compare behavior against `vue-eslint-parser` where compatibility is being claimed.
